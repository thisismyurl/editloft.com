About

Why Editloft exists

Editloft did not start from a blank page. It started from Edit Flow, a plugin that got editorial WordPress right a decade before I touched it. This is the story of what it did, why it stalled, and what rebuilding it actually meant.

Where this came from

Edit Flow’s history

Edit Flow was built by Automattic, Mohammad Jangda, and Daniel Bachhuber, with a copyright span of 2009 to 2019. It was one of the first plugins to treat WordPress as a tool for a team rather than a single writer. It gave WordPress custom post statuses, so a story could be more than draft or published. It gave WordPress an editorial calendar, a story budget view, and editorial comments for the conversation a desk has about its own work. If you ran an editorial team on WordPress in the 2010s, there is a good chance you ran it on Edit Flow. The ideas held up. That is worth saying plainly, because everything Editloft does is downstream of that original thinking.

The platform moved

Why it stalled

Edit Flow was written for the WordPress of its time, and that WordPress had a different editor. When the block editor arrived in 2018, the ground underneath every plugin shifted. Code written against the old editor did not vanish, but it aged, the way a house wired in the 1970s still stands and still needs rethinking before you add a modern kitchen. Edit Flow still exists and still installs. It simply carries fifteen years of architecture built for a version of WordPress that has moved on. That is a fact of platform change, not a failing of the people who wrote the plugin. Software ages against the platform beneath it whether anyone touches it or not.

What changed underneath

What “rebuilt” actually means

Here is how I think about it: keep the editorial discipline, rewrite the underlying machinery for modern WordPress. The idea is not to reinvent how editorial teams think. They already had it right.

So the workflow you get from Editloft will feel familiar to anyone who knew Edit Flow. Underneath, the plumbing is written for the platform that exists now: the block editor, Full Site Editing (FSE, WordPress’s block-based system for editing an entire site), and a current PHP baseline. It requires WordPress 6.4 or newer and PHP 7.4 or newer. The visible discipline is inherited. The machinery under it is new.

Who’s building it

Who’s building it

I’m Christopher Ross. I have been building for the web since 1996 and working in WordPress since 2007, which means I was around for the platform Edit Flow was written for and around for the shift that left it behind. I build tools for the way editorial teams actually work, and I gave a talk on this way of working, “Make a Living Giving It Away,” that was accepted at WordCamp US 2026. Editloft is part of that same practice: useful software, given away, kept honest.

The roadmap

One module at a time, in the open

I am rebuilding Editloft one module at a time, in the open, and I would rather tell you what is missing than imply it is finished. The modules that exist today are custom post statuses (the heart of it), editorial comments, the editorial calendar, editorial metadata, notifications, the dashboard, an audit trail, and settings.

What is not here yet: the story budget module. Edit Flow had one. Editloft does not, not yet. I will not pretend otherwise, and I will not claim feature parity I have not earned. More modules are coming, added one at a time, where you can watch them land.

Where the code lives

Editloft is public. The code lives on GitHub at github.com/thisismyurl/editloft, licensed under the GNU General Public License version 2 or later (GPLv2). You can read it, run it, fork it, and file against it. The plugin header still carries the original Edit Flow copyright line from Jangda, Bachhuber, and Automattic, with portions copyright 2024 to 2025 Christopher Ross. The lineage stays visible on purpose. That is how the GPL is meant to work, and it is the reason any of this was possible.
